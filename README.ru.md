# Parkamat 17

[English](README.md) · [Русский](README.ru.md)

Приложение для Android, которое выглядит как обычный конвертер единиц измерения, а за придуманным пользователем секретным кодом держит полноценный инструмент стеганографии в картинках

## Что это

Parkamat 17 — форк, собранный из двух открытых проектов:

- **[Steganofy](https://github.com/mstaudt/Steganofy)** — стеганография в изображениях для Android. Прячет произвольные данные (текст или файлы) в младшие биты пикселей PNG и достаёт их обратно, при желании с шифрованием AES-256;
- **[UnitConverterUltimate](https://github.com/physphil/UnitConverterUltimate)** — подробный конвертер единиц измерения. Коэффициенты перевода и логика температур взяты отсюда

Смысл затеи — правдоподобное отрицание: приложение и выглядит, и ведёт себя как обычный конвертер. В интерфейсе ничто не намекает, что внутри есть что-то ещё. Попасть в стеганографию можно только через комбинацию, которую пользователь задаёт сам

## Секретная комбинация

При первом запуске открывается одноразовый экран настройки, где пользователь выбирает:

1. **Категорию** (например, объём);
2. **Единицу, из которой переводим** (например, жидкие унции);
3. **Единицу, в которую переводим** (например, миллилитры);
4. **Секретное число**

Дальше ввод ровно этой комбинации в конвертере молча открывает экран стеганографии вместо результата. Ни кнопки, ни подписи, ни пункта меню, ведущих туда, нет. На экране настройки можно нажать «пропустить», тогда секрет не работает вообще

Комбинация лежит локально в SharedPreferences и никуда не уходит. Очистка данных приложения в системных настройках сбрасывает её и возвращает экран настройки

## Почему шифрование может не получиться

Данные ложатся в два младших бита каждого байта пикселя, и прозрачность их убивает. Битмапы `ARGB_8888` хранятся с premultiplied alpha: Skia при декодировании умножает R, G и B на `alpha / 255`, а при сборке PNG делит обратно, и оба раза с округлением. Там, где альфа меньше 255, младшие биты такой круг не переживают, поэтому данные сохраняются только в полностью непрозрачных пикселях. Картинка с альфа-каналом поэтому может проглотить короткий пароль и подавиться длинным текстом — смотря насколько далеко данные дотянутся до прозрачной области

Гадать не приходится: приложение проверяет каждую запись целиком. Как только PNG собран, он декодируется обратно, и данные извлекаются тем же паролем. Если результат не совпал с исходным побайтово, то ничего не сохраняется, а пользователю предлагается взять другую картинку. Эта проверка и позволяет без опаски пробовать любое изображение — битый файл до диска не доезжает

## Чтение носителя

Картинка читается напрямую из MediaStore, а не по тому uri, который отдаёт Photo Picker. За uri пикера стоит его собственная база, и она может держать снимок файла, снятый до перезаписи — из-за этого раньше нельзя было спрятать данные в картинку и сразу расшифровать её же, приложению подсовывало прежнее содержимое. Разрешение `READ_MEDIA_IMAGES` запрашивается при первом выборе файла; отказ ничего не ломает, приложение откатывается на поток от пикера

## Требования

Android 15 (API 35) или новее. Кода для совместимости со старыми версиями в проекте нет

## Сборка

```
./gradlew assembleRelease
```

APK появится в `app/build/outputs/apk/release/` под именем `Parkamat17-<версия>.apk`

**Тулчейн**

| | |
|---|---|
| Gradle | 8.7 |
| Android Gradle Plugin | 8.6.1 |
| Kotlin | 1.9.0 |
| Gradle JDK | 17 или 21 |
| Source/target compatibility | 17 |
| compileSdk / targetSdk | 35 |
| minSdk | 35 |

JDK, на котором работает сам Gradle, и уровень байткода, в который компилируется проект, — две разные настройки. Gradle одинаково нормально живёт и на 17, и на 21, выбирается в *Settings → Build, Execution, Deployment → Build Tools → Gradle → Gradle JDK*. А вот `compileOptions` и `jvmTarget` — другая история: оба модуля (`app` и `lib-steganofy`) обязаны объявить одно и то же значение, иначе сборка падает с несовпадением JVM target. AGP 8.6.1 держит максимум compileSdk 35, так что шаг дальше Android 15 начинается с обновления плагина

**Версионирование**

`versionCode` и `versionName` генерируются, а не прописаны руками. Счётчик в `app/version.properties` растёт на каждой реальной сборке (задачи `assemble`, `bundle` или `install`) и не меняется от синхронизации Gradle. Файл локальный для каждой машины, поэтому номера версий не идут подряд между копиями репозитория
